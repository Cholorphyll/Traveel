Absolutely — Module 9 should be the place where “candidate scoring” becomes precise and slot-specific, rather than trying to make one universal score solve everything.
That’s the right architecture.
Your earlier broad feed score should not decide the final winner directly.
Instead, it should become:
MODULE 9 — SLOT RANKING ENGINE
Final Implementation Spec
Purpose: Choose the best exact item or exact collection inside the slot type already selected by the Sequence Planner.
This module answers:
“Now that we know what kind of thing should come next… which exact candidate is best for this slot right now?”

* relevance
* structural role suitability
* opportunity
* action horizon
* route fit
* sequence fit
* comfort fit
* etc.
But those signals are not final ranking.

9.4 Universal Ranking Pipeline
Every slot should follow the same 6-stage pipeline.
________________


Stage 1 — Candidate Pool Restriction
Only allow candidates that are valid for this slot.
Example:
* Anchor slot → only major structural anchors / anchor-compatible collections
* Recovery slot → only low-friction, restorative, decompression-friendly candidates
* Hero slot → only unusually high-opportunity or “trip-defining” items
* Need-State collection slot → only collection-capable clusters
________________


Stage 2 — Hard Eligibility Gates
Before scoring, eliminate things that simply should not compete.
Examples:
* closed right now
* too far for current time window
* impossible detour
* already completed
* duplicates nearby
* violates current fatigue threshold
* low confidence item
* weak review floor for food slot
These should set:
is_eligible = 0
eligibility_reason = 'closed_now'


________________


Stage 3 — Slot Formula Scoring
Each slot gets a custom weighted formula.
This is the main ranking score.
________________


Stage 4 — Penalty Layer
After scoring, apply penalties for:
* repetition
* category oversaturation
* “too similar to previous items”
* route awkwardness
* fatigue mismatch
* feed monotony
________________


Stage 5 — Tie-Breaking
If final scores are close:
1. Lower travel friction wins
2. Higher structural value wins
3. Higher review strength wins
4. Higher uniqueness wins
5. Lower uncertainty wins
________________


Stage 6 — Winner + Fallbacks
Store:
* winner
* next 3–10 alternatives
* score breakdown
________________


9.5 Required Signal Philosophy
Before formulas, define how each field should be interpreted.
Every slot score should use normalized fields:
Standard normalization:
All scoring fields should be in:
0.0000 → 1.0000


Where:
* 0 = poor / irrelevant
* 1 = ideal for this signal
This is critical because weighted formulas become interpretable.

9.6.1 base_relevance_score
Meaning
This is the carry-forward score from your earlier global ranking / feed suitability engine.
It is not final ranking anymore.
It is only the candidate’s general worthiness in the current trip state.
What it should represent
A blended prior of:
* user intent match
* destination relevance
* popularity
* quality
* travel usefulness
* broad situational relevance
Recommended formula
If you already have it, reuse it. Otherwise:
base_relevance_score =
 0.20 * popularity_score
+0.15 * review_strength
+0.15 * uniqueness
+0.15 * structural_importance
+0.10 * context_fit
+0.10 * route_fit
+0.10 * trip_important_score
+0.05 * timing_fit


SQL population example
UPDATE feed_slot_candidates
SET base_relevance_score =
    (
      0.20 * popularity_score +
      0.15 * review_strength +
      0.15 * uniqueness +
      0.15 * structural_importance +
      0.10 * context_fit +
      0.10 * route_fit +
      0.10 * trip_important_score +
      0.05 * timing_fit
    );


________________


9.6.2 structural_importance
Meaning
How much this candidate matters to the trip’s skeleton, not just as a nice option.
This answers:
“If the user skipped this, would the day / area / city feel structurally incomplete?”
High structural importance examples
* Eiffel Tower in Paris
* Colosseum in Rome
* main old town district
* iconic seafront
* signature bazaar
* main cathedral / main square
* “you came here for this” item
Low structural importance examples
* random coffee stop
* minor alley mural
* average dessert shop
* generic side museum
How to calculate it
Use:
* popularity percentile within city
* landmark significance
* “anchor” classification
* review count dominance
* itinerary centrality
* appearance frequency in top city guides (optional)
* role assignment output
Good formula
structural_importance =
 0.35 * anchor_probability
+0.25 * city_popularity_percentile
+0.20 * review_volume_strength
+0.10 * uniqueness
+0.10 * district_centrality


Field sub-definitions
anchor_probability
Probability this item behaves as a trip anchor.
Can come from Role Assignment Engine.
city_popularity_percentile
Popularity rank among same-city items.
review_volume_strength
Normalized review count strength.
district_centrality
How central this item is within tourist movement clusters.
Example SQL
UPDATE feed_slot_candidates f
JOIN candidate_features c
  ON f.candidate_type = c.candidate_type
 AND f.candidate_id = c.candidate_id
SET f.structural_importance =
    (
      0.35 * c.anchor_probability +
      0.25 * c.city_popularity_percentile +
      0.20 * c.review_volume_strength +
      0.10 * c.uniqueness_score +
      0.10 * c.district_centrality
    );

9.6.3 trip_progress_value
Meaning
How much this candidate advances the trip meaningfully right now.
This is not “good in general.”
It is:
“Does doing this now move the traveler forward in the journey?”
High trip progress examples
* entering the old town after arrival
* reaching the main viewpoint before sunset
* doing the key museum before closing
* eating before a long route segment
* picking up transport before departure
Low trip progress examples
* a random souvenir shop while still hungry and far from the anchor
* minor detour before major unfinished anchors
Formula
trip_progress_value =
 0.30 * anchor_advancement
+0.20 * sequence_alignment
+0.20 * route_position_value
+0.15 * urgency_alignment
+0.15 * completion_contribution


How to derive sub-signals
anchor_advancement
Does this move the user toward current / next anchor?
sequence_alignment
How well this matches the expected next feed phase.
route_position_value
Is it well placed in the current movement arc?
urgency_alignment
Does it become less useful later?
completion_contribution
Does it help complete a district / cluster / trip chapter?
SQL example
UPDATE feed_slot_candidates
SET trip_progress_value =
    (
      0.30 * anchor_advancement +
      0.20 * sequence_alignment +
      0.20 * route_position_value +
      0.15 * urgency_alignment +
      0.15 * completion_contribution
    );

9.6.5 proximity_score
Meaning
How geographically convenient this candidate is right now.
This is not raw distance.
It is a normalized “closeness utility.”
Formula
Best done as a piecewise decay rather than linear.
Walking-city example
0–300m     = 1.00
301–700m   = 0.85
701–1200m  = 0.65
1201–2000m = 0.40
2000m+     = 0.15


SQL example
UPDATE feed_slot_candidates
SET proximity_score =
    CASE
        WHEN distance_m <= 300 THEN 1.00
        WHEN distance_m <= 700 THEN 0.85
        WHEN distance_m <= 1200 THEN 0.65
        WHEN distance_m <= 2000 THEN 0.40
        ELSE 0.15
    END;


You can also make this dynamic by city mode:
* old town walking city
* spread-out car city
* island / beach destination
* mountain route destination

9.6.7 fatigue_compatibility
Meaning
How appropriate this candidate is for the user’s current likely energy state.
This answers:
“Given how the traveler probably feels now… is this a good fit?”
Inputs
* walking already done
* recent dwell load
* heat / weather drain
* current time
* previous feed intensity
* expected effort of candidate
Formula
fatigue_compatibility =
 1 - ABS(current_fatigue_level - candidate_energy_demand)


Where both are normalized 0–1.
Clamp to 0–1.
Example
If:
* current fatigue = 0.80
* candidate demand = 0.20
Then this might actually be good for a recovery slot, but poor for an anchor slot.
So use carefully.
A better practical version:
fatigue_compatibility =
 1 - MAX(0, candidate_energy_demand - current_energy_capacity)


SQL example
UPDATE feed_slot_candidates
SET fatigue_compatibility =
    GREATEST(0, 1 - GREATEST(0, candidate_energy_demand - current_energy_capacity));

9.6.16 review_strength
Meaning
How strong the quality confidence is, combining rating and review volume.
This should not just be raw average rating.
Better formula
review_strength =
 0.60 * bayesian_rating_score
+0.40 * review_volume_strength


Bayesian rating score
Recommended:
bayesian_rating =
((v / (v + m)) * R) + ((m / (v + m)) * C)


Where:
* R = candidate average rating
* v = review count
* C = global average rating
* m = minimum reviews threshold (e.g. 100)
Then normalize to 0–1.
SQL example
UPDATE candidate_features
SET bayesian_rating_score =
    (
      ((review_count / (review_count + 100.0)) * avg_rating) +
      ((100.0 / (review_count + 100.0)) * 4.2)
    ) / 5.0;


Then:
UPDATE feed_slot_candidates f
JOIN candidate_features c
  ON f.candidate_type = c.candidate_type
 AND f.candidate_id = c.candidate_id
SET f.review_strength =
    (0.60 * c.bayesian_rating_score) +
    (0.40 * c.review_volume_strength);

9.8 Penalty Layer (Very Important)
Without penalties, the engine will over-select:
   * same category repeatedly
   * same energy repeatedly
   * same district repeatedly
   * similar experiences repeatedly
That makes feeds feel robotic.
________________


9.8.1 repetition_penalty
Meaning
Penalty for repeating similar item types too soon.
Example logic
If last 3 items already include:
   * 2 museums → penalize another museum
   * 2 cafés → penalize another café
   * 2 viewpoints → penalize another viewpoint
Formula
repetition_penalty =
 min(0.25, recent_type_repeat_count * 0.08)


SQL example
UPDATE feed_slot_candidates
SET repetition_penalty =
    LEAST(0.25, recent_type_repeat_count * 0.08);


________________


9.8.2 redundancy_penalty
Meaning
Penalty if candidate is too similar to recently surfaced options.
Examples:
   * same kind of church
   * same waterfront photo stop
   * same brunch style
   * same market experience
Formula
redundancy_penalty =
 0.5 * semantic_similarity_to_recent


Where similarity is normalized 0–1.
________________


9.8.3 oversaturation_penalty
Meaning
Penalty if too much of the same district / energy / category has already dominated the feed.
Formula
oversaturation_penalty =
 0.4 * category_saturation
+0.3 * area_saturation
+0.3 * energy_saturation


________________


9.8.4 fatigue_penalty
Meaning
Penalty if this candidate adds too much effort right now.
Formula
fatigue_penalty =
 GREATEST(0, candidate_energy_demand - current_energy_capacity) * 0.4


________________


9.8.5 Final Penalty Total
slot_penalty_total =
 repetition_penalty
+ redundancy_penalty
+ oversaturation_penalty
+ fatigue_penalty


SQL
UPDATE feed_slot_candidates
SET slot_penalty_total =
    repetition_penalty +
    redundancy_penalty +
    oversaturation_penalty +
    fatigue_penalty;


________________


9.9 Final Slot Score
slot_score_final =
 GREATEST(0, slot_score_raw - slot_penalty_total)


SQL
UPDATE feed_slot_candidates
SET slot_score_final =
    GREATEST(0, slot_score_raw - slot_penalty_total)
WHERE is_eligible = 1;


For ineligible rows:
UPDATE feed_slot_candidates
SET slot_score_final = 0
WHERE is_eligible = 0;


________________


9.10 Ranking Query
SET @r := 0;


UPDATE feed_slot_candidates c
JOIN (
    SELECT id,
           (@r := @r + 1) AS rn
    FROM feed_slot_candidates
    WHERE session_id = 'abc123'
      AND feed_moment_id = 17
      AND slot_type = 'ANCHOR'
      AND is_eligible = 1
    ORDER BY slot_score_final DESC,
             travel_time_min ASC,
             structural_importance DESC,
             review_strength DESC,
             uniqueness DESC
) ranked
ON c.id = ranked.id
SET c.rank_position = ranked.rn;


Then winner:
UPDATE feed_slot_candidates
SET selected = 1
WHERE session_id = 'abc123'
  AND feed_moment_id = 17
  AND slot_type = 'ANCHOR'
  AND rank_position = 1;

For collection slots like:

You should create collection candidates.

Recommended collection table
CREATE TABLE candidate_collections (

    collection_type VARCHAR(100) NOT NULL,
    area_id BIGINT NULL,
    anchor_id BIGINT NULL,
    title VARCHAR(255),

);

Collection scoring logic
A collection score should blend:
   * top 3 member quality
   * compactness
   * option diversity
   * confidence consistency
   * route convenience
Example formulas
collection_review_strength =
 0.50 * avg(top3_review_strength)
+0.25 * median(review_strength)
+0.25 * quality_consistency


ease_of_choice =
 0.35 * compactness
+0.25 * quality_consistency
+0.20 * low_noise_ratio
+0.20 * option_clarity


need_state_match =
 0.50 * % of members matching current need
+0.25 * best_member_need_match
+0.25 * practical_relief_fit

9.12 Hard Eligibility Rules by Slot Type
This is important. Different slots should reject different things.
________________


Anchor Slot Hard Gates
Reject if:
   * closed / inaccessible
   * route detour too high
   * already completed
   * structurally redundant
   * too weak compared to current anchor
________________


Hero Slot Hard Gates
Reject if:
   * opportunity window expired
   * weak payoff
   * poor feasibility
   * too similar to recent hero
________________


Recovery Slot Hard Gates
Reject if:
   * high effort
   * high queue
   * high crowd
   * low seating / no relief
________________


Need-State Collection Slot Hard Gates
Reject if:
   * too sparse
   * too confusing
   * low confidence quality
   * too far off route
   * currently mismatched to active need

9.14 Strong Recommendation: Don’t Over-Use One Formula Across All Slots
This is one of the biggest mistakes teams make.
A single “best POI score” sounds elegant — but it creates bad travel behavior because:
   * best lunch area ≠ best hero moment
   * best recovery move ≠ best anchor
   * best browse cluster ≠ best must-do
   * best next step ≠ best overall attraction
That’s exactly why this module is necessary.
