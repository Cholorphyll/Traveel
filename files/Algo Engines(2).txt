Module 3 - STRUCTURAL IMPORTANCE ENGINE
SQL / TABLE / COMPUTATION SPEC (FINAL)
________________


0) PURPOSE OF THIS MODULE
This module computes:
How much an entity matters to the structural architecture of a trip
This is not:
* time-sensitive relevance
* weather fit
* “best nearby now”
* user-specific personalization
This is:
* trip spine importance
* district importance
* collective destination importance
* supportive route importance
________________


1) FINAL OUTPUTS OF THIS MODULE
Each entity should get:
* poi_anchor_score
* composite_anchor_score
* collective_destination_score
* soft_anchor_score
* trip_value_score
* structural_importance_score
* structural_class
These should be stored in a dedicated table.
________________


2) WHAT THIS MODULE WILL NEED AS INPUT
This module should read from:
* Sight
* Restaurant
* Experience
* optional anchor/sub-anchor mapping table
* optional review-signal mapping table
* Location table
* optional graph tables later
For now, we will make this buildable without requiring your full graph engine.
That’s important.
________________

You should create 4 tables for this engine:
1. entity_structural_base

4) TABLE 1 — entity_structural_base
This is the unified normalized input layer for the engine.
It pulls all entities from Sight, Restaurant, and Experience into one common scoring table.
This makes everything much easier downstream.
________________


SQL — Create entity_structural_base
CREATE TABLE entity_structural_base (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,


    entity_type ENUM('sight','restaurant','experience') NOT NULL,
    entity_id BIGINT UNSIGNED NOT NULL,
    location_id BIGINT UNSIGNED DEFAULT NULL,


    title VARCHAR(255) DEFAULT NULL,


    lat DECIMAL(10,8) DEFAULT NULL,
    lng DECIMAL(11,8) DEFAULT NULL,


    category VARCHAR(150) DEFAULT NULL,
    sub_category VARCHAR(150) DEFAULT NULL,


    aggregate_rating DECIMAL(8,4) DEFAULT NULL,
    review_count INT DEFAULT NULL,


    popularity_score DECIMAL(8,4) DEFAULT NULL,
    recommendation_score DECIMAL(8,4) DEFAULT NULL,


    is_landmark_manual TINYINT(1) DEFAULT 0,
    is_unique_manual TINYINT(1) DEFAULT 0,
    is_destination_restaurant TINYINT(1) DEFAULT 0,
    is_signature_experience TINYINT(1) DEFAULT 0,


    category_anchor_prior DECIMAL(8,4) DEFAULT NULL,
    category_uniqueness_prior DECIMAL(8,4) DEFAULT NULL,


    city_review_percentile DECIMAL(8,4) DEFAULT NULL,
    local_density_score DECIMAL(8,4) DEFAULT NULL,
    local_category_density DECIMAL(8,4) DEFAULT NULL,
    city_category_density DECIMAL(8,4) DEFAULT NULL,


    anchor_signal_coverage DECIMAL(8,4) DEFAULT NULL,
    tag_distinctiveness_score DECIMAL(8,4) DEFAULT NULL,


    computed_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,


    UNIQUE KEY uq_entity (entity_type, entity_id),
    KEY idx_location (location_id),
    KEY idx_type (entity_type),
    KEY idx_rating_reviews (aggregate_rating, review_count),
    KEY idx_coords (lat, lng)
);

12) RELATIVE POSITION FIELDS
These are derived, not directly stored in source tables.
These are very important.
________________


12.1 city_review_percentile
Meaning
Where this entity ranks in review count relative to all entities in the city.
Example
If an entity is in the top 5% by reviews in London, this should be high.
Why needed
Raw review counts are misleading across cities.
Percentiles are much better.
How to calculate
For each location_id, compute percentile rank of review_count.
SQL logic (conceptually)
PERCENT_RANK() OVER (
    PARTITION BY location_id
    ORDER BY review_count
)


Store result as 0.00–1.00.
________________


12.2 local_density_score
Meaning
How dense the surrounding entity environment is.
Why needed
Used for:
* composite anchor logic
* collective destination logic
* cluster membership
* co-visit strength
How to calculate
For each entity:
Count nearby entities within a walk radius.
Recommended radius
Use multiple radii:
* 250m
* 500m
* 900m
Then blend them.
Recommended formula
local_density_score =
  0.45 * nearby_entities_250m_norm +
  0.35 * nearby_entities_500m_norm +
  0.20 * nearby_entities_900m_norm


Normalize city-wide afterward.
________________


12.3 local_category_density
Meaning
How many nearby places of the same category exist.
Why needed
Used for uniqueness.
Example
If a café sits in a street with 40 cafés nearby, uniqueness should drop.
How to calculate
Count nearby same-category entities within 500m / 800m.
________________


12.4 city_category_density
Meaning
How saturated this category is across the whole city.
Why needed
Also used for uniqueness.
Example
If there are 2,500 generic restaurants in the city, that category is highly replaceable.
How to calculate
For each category within location:
count(category) / total_entities_in_location


Or raw count normalized.
________________


13) SIGNAL / DISTINCTIVENESS FIELDS
These are where your signal-anchor mapping becomes useful.
This is a very strong addition to your engine.
________________


13.1 anchor_signal_coverage
Meaning
How richly this entity expresses structurally meaningful anchor/sub-anchor signals.
Example
If an entity strongly maps to:
* heritage
* culture
* iconic
* family
* local identity
* nightlife
* culinary destination
then its structural identity is richer.
Why needed
This helps distinguish:
* generic places
from
* structurally expressive places
How to populate
From your signal_anchor_map / review-derived signal tables.
Simple way
For each entity:
   * count distinct meaningful anchor/sub-anchor signals
   * weighted by confidence / frequency
Example formula
anchor_signal_coverage =
  weighted_distinct_signal_count / max_city_signal_count


Normalize to 0–1.
________________


13.2 tag_distinctiveness_score
Meaning
How unusual / specific the entity’s identity is compared to others nearby.
Why needed
Useful for uniqueness and trip value.
Example
A generic brunch café → low
A Victorian science museum or iconic spice-market-style restaurant → high
How to populate
Use:
   * rarity of sub-anchors
   * rarity of tags in local radius
   * rarity of experience theme
Practical version
For each entity:
   * take its top anchor/sub-anchor tags
   * compute inverse local frequency
Formula
tag_distinctiveness_score =
  average(inverse_frequency_of_top_tags_in_local_area)

14) HOW TO POPULATE entity_structural_base
You should populate this table in one batch pipeline.
________________


STEP A — Insert normalized entities
Insert all from:
   * Sight
   * Restaurant
   * Experience
Map them into common fields.
________________


Example — Insert from Sight
INSERT INTO entity_structural_base (
    entity_type, entity_id, location_id, title, lat, lng,
    category, sub_category,
    aggregate_rating, review_count, popularity_score, recommendation_score
)
SELECT
    'sight',
    s.id,
    s.location_id,
    s.Name,
    s.Latitude,
    s.Longitude,
    s.Category,
    s.SubCategory,
    s.TAAggregateRating,
    s.TATotalReviews,
    s.PopularityScore,
    s.RecommendationScore
FROM Sight s
WHERE s.Latitude IS NOT NULL
  AND s.Longitude IS NOT NULL;


Do the same for Restaurant and Experience.
________________


STEP B — Update category priors
Use a mapping table.
Create:
CREATE TABLE category_structural_priors (
    category VARCHAR(150) PRIMARY KEY,
    category_anchor_prior DECIMAL(8,4) DEFAULT NULL,
    category_uniqueness_prior DECIMAL(8,4) DEFAULT NULL
);


Then update:
UPDATE entity_structural_base esb
JOIN category_structural_priors csp
  ON esb.category = csp.category
SET
  esb.category_anchor_prior = csp.category_anchor_prior,
  esb.category_uniqueness_prior = csp.category_uniqueness_prior;


________________


STEP C — Compute percentile and density fields
Then populate:
   * city_review_percentile
   * local_density_score
   * local_category_density
   * city_category_density
   * anchor_signal_coverage
   * tag_distinctiveness_score
This is best done in Python or Laravel batch jobs.
It is possible in SQL too, but Python is cleaner for geo calculations.

17) CLUSTER STRENGTH FIELDS
These are very important.
________________


17.1 density_score
Meaning
How dense the cluster is.
How to calculate
Use:
   * entity count per area
   * or average nearest-neighbor compactness
Practical version
Normalize entity count adjusted by cluster radius.
________________


17.2 cohesion_score
Meaning
How spatially tight and coherent the cluster is.
Why needed
A dense but scattered area is weaker than a tight, walkable one.
How to calculate
Use:
   * mean distance to centroid
   * pairwise compactness
   * spatial spread
Tighter cluster = higher score.
________________


17.3 diversity_score
Meaning
How structurally diverse the cluster is.
Why needed
Mixed clusters often make stronger destination zones.
Example
A zone with:
   * attraction + food + experience
is often more structurally powerful than
   * 12 isolated same-type entities
How to calculate
Entropy or mix score across entity types / categories.
________________


17.4 walkability_score
Meaning
How easy it is to experience the cluster on foot.
Practical version
Use:
      * cluster compactness
      * street-network approximation later if needed
      * average internal walking distance proxy
Simple approximation for now
Tighter + denser = more walkable
________________


17.5 anchor_concentration_score
Meaning
How many strong anchor-capable entities exist in the cluster.
Why needed
This is crucial for:
      * composite anchor logic
      * area gravity
How to calculate
After intrinsic scores are computed, sum or average high-anchor entities in cluster.
________________


17.6 destination_gravity_score
Meaning
How destination-worthy the cluster is overall.
Formula
destination_gravity_score =
  0.25 * density_score +
  0.20 * cohesion_score +
  0.15 * diversity_score +
  0.20 * walkability_score +
  0.20 * anchor_concentration_score


This is a key cluster-level field.
________________

21) HOW TO BUILD CLUSTERS (PRACTICAL METHOD)
This is the simplest strong method for your system.
________________


Recommended clustering method
Use DBSCAN on all entities within each location_id.
Recommended starting params for city travel
For walkable city clustering:
         * eps = 350m to 500m
         * min_samples = 4 to 6
You can tune later.
Why DBSCAN is good
It naturally finds:
         * dense pockets
         * irregular shaped clusters
         * walkable zones
That’s ideal for:
         * markets
         * dining streets
         * museum quarters
         * nightlife pockets
________________


Suggested pipeline
For each city (location_id):
         1. pull all entities with coordinates
         2. run DBSCAN on lat/lng projected to meters
         3. assign cluster_id
         4. compute cluster centroid
         5. compute cluster-level metrics
         6. insert cluster members
This is best done in Python.
________________

23) HOW TO CALCULATE EACH FINAL FIELD
Now we get into the actual engine logic.
________________


24) INTRINSIC SUB-SCORES
These should be computed first.
________________


24.1 landmark_strength
Meaning
How much this entity behaves like a landmark / named trip draw.
Formula
landmark_strength =
  0.35 * review_count_norm +
  0.25 * popularity_norm +
  0.20 * category_anchor_prior +
  0.20 * is_landmark_manual


Inputs needed
         * normalized review count
         * popularity_score or recommendation proxy
         * category_anchor_prior
         * manual flag
________________


24.2 fame_strength
Meaning
How known this entity is in city/traveler behavior.
Formula
fame_strength =
  0.45 * city_review_percentile +
  0.30 * rating_confident_score +
  0.25 * popularity_rank_score


Where:
         * rating_confident_score = rating weighted by review confidence
         * popularity_rank_score = normalized popularity rank if available
________________


24.3 uniqueness_strength
Meaning
How hard this place is to replace.
Formula
uniqueness_strength =
  0.25 * (1 - local_category_density_norm) +
  0.20 * (1 - city_category_density_norm) +
  0.20 * tag_distinctiveness_score +
