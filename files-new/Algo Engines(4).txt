MODULE — CONTEXT ENGINE (Final Architecture)
Part 1
1) Core Purpose
The Context Engine determines:
* what kind of place the user is currently in
* what semantic zones exist around them
* which entities naturally belong to that zone
* what feels contextually appropriate right now
This module is not about popularity.
It is about place truth.
It answers:
* “What kind of environment is this?”
* “What belongs here?”
* “What feels natural nearby?”
* “What kind of things should be shown because of where the user is?”
________________


2) What the Context Engine Should Produce
For every user state / route state / anchor state, this engine should output:
* primary_context
* secondary_contexts[]
* active_context_zone
* context_confidence
* context_signature
* entity_context_affinity_score
* entity_context_role
* context_fit_reason
That becomes the semantic foundation used by:
* Eligibility Engine
* Structural Importance Engine
* Opportunity Engine
* Route Engine
* Slot Ranking Engine
* Moment Framing Engine
So this module is central, not cosmetic.
________________


3) Mental Model of the Context Engine
Think of it in 4 layers:
Layer A — Macro Place Identity
“What broad kind of place is this?”
Examples:
* beach
* old town
* waterfront
* lakefront
* mountain village
* marina
* urban core
* arts district
* market district
* temple quarter
* promenade
* parkland
* nightlife strip
* shopping boulevard
* riverside
* countryside edge
________________


Layer B — Semantic Subcontext
“What exact flavor of place is this?”
Examples:
* sunset beach zone
* quiet cove
* family beach
* boardwalk food strip
* heritage walking lane
* nightlife marina edge
* shaded café lane
* elevated viewpoint ridge
* temple approach street
* riverside strolling corridor
* artisan shopping cluster
________________


Layer C — Route Context
“What kind of movement or journey is happening right now?”
Examples:
* arrival context
* scenic wandering context
* exploration context
* lunch context
* golden hour context
* cool-down context
* transition corridor
* destination approach
* evening social context
* end-of-day unwind context
________________


Layer D — Entity Fit
“Does this item belong here right now?”
Examples:
* A beach shack café fits strongly in a beach leisure zone
* A rooftop cocktail bar may fit poorly at 10 AM in a family beach context
* A heritage alley viewpoint fits strongly inside old-town exploration
* A museum gift shop might be weak unless user is in anchor-exit transition
This is what makes recommendations feel human.
________________


4) Final Outputs of the Context Engine
For every active session state, compute:
________________


4.1 Place-Level Outputs
primary_context
The strongest place identity.
Examples:
* beach
* old_town
* waterfront
* marina
* market_district
________________


secondary_contexts
Additional overlapping context tags.
Examples:
["sunset_zone", "food_strip", "walkable_promenade"]


________________


active_context_zone
The exact semantic zone the user is currently inside.
Examples:
* quiet_cove
* heritage_lane
* nightlife_marina_edge
* cliffside_viewpoint_zone
________________


context_confidence
How certain the engine is that the inferred context is correct.
Range:
0.00 – 1.00
________________


context_signature
A compact semantic identity used by downstream engines.
Example:
{
  "primary_context": "beach",
  "secondary_contexts": ["sunset_zone", "walkable", "food_adjacent"],
  "route_context": "golden_hour_exploration"
}


This is extremely useful later.
________________


4.2 Entity-Level Outputs
For each candidate entity, compute:
context_affinity_score
How naturally this entity belongs in the active context.
Range:
0 – 100
________________


entity_context_role
What role it plays in this context.
Examples:
* core_fit
* supporting_fit
* transition_fit
* specialist_fit
* weak_fit
* context_breaker
________________


context_fit_reason
Human-readable reason for logging / debugging.
Examples:
* “Strong sunset-facing fit near waterfront promenade”
* “Useful food support within heritage walking lane”
* “Low semantic fit for quiet scenic zone”
* “Belongs more to nightlife than daytime family beach context”
This field will save you a lot of debugging pain later.

7) How to Detect Primary Context
Now the real logic.
Each candidate context should receive a score.
________________


7.1 primary_context_score
Example:
primary_context_score(context) =
 0.28 * nearby_entity_pattern_score
+ 0.22 * anchor_semantic_score
+ 0.18 * geography_signal_score
+ 0.14 * pedestrian_behavior_score
+ 0.10 * route_alignment_score
+ 0.08 * naming_signal_score


________________


7.2 What Each Part Means
A) nearby_entity_pattern_score
What types of entities dominate nearby?
Examples:
* beach clubs, seaside cafés, sunset points → beach / waterfront
* churches, museums, old lanes, plazas → old_town / historic_core
* bars, lounges, clubs, rooftop dining → nightlife_district
* bazaars, stalls, food courts, shops → market_district
This is one of your strongest signals.
________________


B) anchor_semantic_score
What is the current anchor / subanchor semantically classified as?
If the user is at:
* “Marina Walk” → likely marina / waterfront
* “Old Port Gate” → likely historic_core / waterfront
* “Sunset Beach Access” → likely beach / sunset_zone
This gives strong structural prior.
________________


C) geography_signal_score
What does the physical environment imply?
Examples:
* near coastline → beach / waterfront
* near lake edge → lakefront
* elevated terrain / cliff → hilltop / viewpoint zone
* dense pedestrian streets → market / old town / promenade
________________


D) pedestrian_behavior_score
What kind of movement does this area encourage?
Examples:
* strolling → promenade / old town / waterfront
* stop-and-look → viewpoint / heritage lane
* flow-through → transition corridor
* short dwell clusters → food strip / market lane
This can be inferred later from session behavior too.
________________


E) route_alignment_score
Does this context align with where the user is heading?
If the route is clearly pulling toward a waterfront or anchor district, boost that context.
________________


F) naming_signal_score
Entity names and area labels often reveal context.
Examples:
* “Marina Walk”
* “Old Town Square”
* “Beach Road”
* “Sunset Point”
* “Heritage Street”
* “Bazaar Lane”
This is a surprisingly useful lightweight signal.
________________


8) How to Detect Secondary Contexts
Primary context tells you what place this broadly is.
Secondary contexts tell you what is happening inside it.
This is much more important for feed quality.
________________


8.1 Example
A place may be:
* primary_context = waterfront
but simultaneously have:
* secondary_contexts = ["sunset_zone", "food_strip", "walkable", "romantic_zone"]
That gives the engine much better taste.
________________


8.2 secondary_context_score
secondary_context_score(subcontext) =
 0.30 * micro_cluster_match
+ 0.20 * entity_density_signal
+ 0.18 * route_micro_position
+ 0.14 * dwell_pattern_signal
+ 0.10 * time_of_day_relevance
+ 0.08 * naming_signal


________________


8.3 Examples
sunset_zone
Strong if:
* west-facing scenic points nearby
* many “sunset” or “viewpoint” signals
* golden hour timing
* open horizon / waterfront / ridge
________________


food_strip
Strong if:
* restaurant density is high
* food entities cluster tightly
* short walking transitions between eateries
* dwell potential is high
________________


heritage_lane
Strong if:
* heritage attractions cluster tightly
* walking paths are narrow and sequential
* visual stop points are frequent
* naming or attraction tags suggest old-town character
________________


transition_corridor
Strong if:
* user is moving between two stronger anchors
* entities nearby are weak as destinations but useful as in-between inserts
This one is very valuable and most systems miss it.
________________

10.1 Table: context_zones
This is the master table for semantic place zones.
CREATE TABLE context_zones (
  context_zone_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  entity_location_id BIGINT NOT NULL,
  zone_name VARCHAR(255) DEFAULT NULL,
  primary_context VARCHAR(100) DEFAULT NULL,
  active_context_zone VARCHAR(100) DEFAULT NULL,

  center_lat DECIMAL(10,8) DEFAULT NULL,
  center_lng DECIMAL(11,8) DEFAULT NULL,
  radius_meters INT DEFAULT NULL,


  context_confidence DECIMAL(5,4) DEFAULT NULL,
  context_signature JSON DEFAULT NULL,


  source_url VARCHAR(500) DEFAULT NULL,
  is_active TINYINT(1) DEFAULT 1,


  created_at TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,


  INDEX idx_location (entity_location_id),
  INDEX idx_primary_context (primary_context),
  INDEX idx_active_context (active_context_zone)
);


________________


Why this table matters
This lets you say:
“This exact part of the city behaves like a sunset promenade.”
“This pocket behaves like a heritage walking lane.”
“This cluster behaves like a nightlife marina zone.”
That is gold for downstream ranking.
________________


10.2 Table: entity_context_affinity
This stores how well each entity fits different contexts.
CREATE TABLE entity_context_affinity (
  entity_context_affinity_id BIGINT PRIMARY KEY AUTO_INCREMENT,


  entity_type ENUM('sight','restaurant','experience') NOT NULL,
  entity_id BIGINT NOT NULL,
  entity_location_id BIGINT NOT NULL,


  primary_context VARCHAR(100) DEFAULT NULL,
  active_context_zone VARCHAR(100) DEFAULT NULL,


  context_affinity_score DECIMAL(6,2) DEFAULT NULL,

  distance_score DECIMAL(6,2) DEFAULT NULL,
  line_of_sight_score DECIMAL(6,2) DEFAULT NULL,
  review_signal_score DECIMAL(6,2) DEFAULT NULL,
  category_match_score DECIMAL(6,2) DEFAULT NULL,
  semantic_match_score DECIMAL(6,2) DEFAULT NULL,
  time_fit_score DECIMAL(6,2) DEFAULT NULL,

  updated_at TIMESTAMP NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,


  INDEX idx_entity_lookup (entity_type, entity_id),
  INDEX idx_location (entity_location_id),
  INDEX idx_context (primary_context, active_context_zone),
  INDEX idx_affinity (context_affinity_score)
);

11) How to Compute context_affinity_score
Now the heart of the module.
This decides:
“How naturally does this entity belong in the current place context?”
This should not be pure distance.
________________


11.1 Final Recommended Formula
context_affinity_score =
 0.24 * distance_score
+ 0.18 * semantic_match_score
+ 0.14 * category_match_score
+ 0.14 * line_of_sight_score
+ 0.12 * review_signal_score
+ 0.10 * time_fit_score
+ 0.08 * cluster_fit_score


Normalize final score to:
0 – 100
________________


12) Meaning of Each Context Affinity Component
________________


12.1 distance_score
Closer things usually belong more naturally.
But use contextual decay, not blunt distance.
Example:
* In old town: 120m is still excellent
* In beach/resort strip: 450m may still feel natural
* In hill context: 300m with elevation penalty may be weaker
So distance should be context-sensitive.
________________


12.2 semantic_match_score
How semantically aligned is the entity with the detected place identity?
Examples:
* beach shack café in beach zone → high
* rooftop cocktail bar in marina nightlife zone → high
* temple souvenir lane in heritage context → high
* indoor gaming arcade in quiet cove → low
This is one of your strongest signals.
________________


12.3 category_match_score
Does the entity category naturally belong here?
Examples:
* scenic viewpoint in cliff edge zone → high
* seafood place near waterfront → high
* artisanal market stall in heritage lane → high
This is more structured than free-form semantics.
________________


12.4 line_of_sight_score
Can this place be visually or experientially connected to the context?
Examples:
* sunset café overlooking sea → very high
* hidden alley café behind main route → moderate
* basement bar away from visible context → lower unless nightlife context is active
This is incredibly useful for scenic places.
________________


12.5 review_signal_score
Do users implicitly validate this place-context fit?
Examples:
* Reviews mention “great sea views”, “perfect after beach”, “nice after sunset”
* Reviews mention “best in old town”, “beautiful walk from square”
This is review semantics, not just star rating.
Very powerful later.
________________


12.6 time_fit_score
Does it fit the current moment?
Examples:
* brunch café in morning → high
* sunset viewpoint at golden hour → very high
* loud nightlife venue at 11 AM → weak
* lantern-lit alley at evening → high
This is where Context Engine starts blending into Moment Engine later.
________________


12.7 cluster_fit_score
Does it sit inside a coherent semantic cluster?
Examples:
* a restaurant inside a dense marina dining strip → strong
* a random isolated shop far from any related cluster → weak
This helps remove weird outliers.
________________


13) Entity Context Roles (Very Important)
Every candidate should also get a context role.
This helps downstream ranking a lot.
________________


Recommended entity_context_role values
core_fit
supporting_fit
transition_fit
specialist_fit
scenic_fit
social_fit
utility_fit
weak_fit
context_breaker


________________


Meaning
core_fit
This entity is deeply native to the place.
Example:
* beachfront sunset viewpoint in sunset beach zone
________________


supporting_fit
Very natural, but not defining.
Example:
* gelato shop in promenade zone
________________


transition_fit
Useful because it helps movement between stronger anchors.
Example:
* café between two major sights
________________


specialist_fit
Highly relevant to a specific user intent, but not universally place-defining.
Example:
* local craft workshop in heritage district
________________


scenic_fit
Fits mainly because of environmental or visual payoff.
________________


social_fit
Fits because it supports energy / gathering / nightlife / group vibe.
________________


utility_fit
Useful but not place-defining.
Example:
* water stop, casual snack, quick recharge
________________


weak_fit
Some relevance, but not strongly belonging.
________________


context_breaker
Nearby, but semantically wrong for this place/moment.
This is useful to suppress noise.
________________


14) Context Confidence
The engine should not pretend certainty when signals are weak.
Compute:
context_confidence =
 0.40 * top_context_margin
+ 0.25 * signal_density
+ 0.20 * anchor_support
+ 0.15 * route_consistency


Range:
0.00 – 1.00
________________


Why this matters
If confidence is low:
* allow broader candidate diversity
* reduce hard suppression
* let Opportunity Engine take more control
If confidence is high:
* become more selective
* suppress context breakers harder
* tighten semantic fit requirements
This is a very useful control knob.
________________


15) Context Signature (Downstream Superpower)
Build a compact machine-readable semantic state.
Example:
{
  "primary_context": "waterfront",
  "secondary_contexts": ["sunset_zone", "food_strip", "promenade_zone"],
  "route_context": "golden_hour_exploration",
  "context_confidence": 0.87
}


This should be passed downstream to all ranking modules.
This becomes the “semantic environment state” of the session.
________________


16) Recommended Pipeline for Context Engine
This is the clean execution flow.
________________


CONTEXT ENGINE PIPELINE
Step 1 — Gather Nearby Evidence
Fetch nearby:
* anchors / subanchors
* sights
* restaurants
* experiences
* context zones
* route path
* geography signals
________________


Step 2 — Score Macro Contexts
Compute score for all possible primary_context candidates.
Pick:
* top 1 as primary_context
* top 2–4 as backup context priors
________________


Step 3 — Score Secondary Contexts
Compute:
* secondary_contexts
* active_context_zone
________________


Step 4 — Compute context_confidence
Determine how reliable the context inference is.
________________


Step 5 — Build context_signature
Package final semantic state.
________________


Step 6 — Score Entity Context Affinity
For each candidate entity:
* compute context_affinity_score
* assign entity_context_role
* generate context_fit_reason
________________


Step 7 — Write Results to Context Layer
Persist to:
* context_zones
* entity_context_affinity
________________

Structural Importance Engine

Opportunity Engine

* what feels naturally insertable right now?

Route Engine

Slot Ranking Engine

Moment Framing Engine

19) Final Recommendation — How You Should Build It
If I were building your production version, I would structure Context Engine around three permanent concepts:
________________


A) Controlled Context Taxonomy
You define:
* allowed macro contexts
* allowed subcontexts
* allowed roles
This prevents semantic mess.
________________


B) Context Zone Layer
Persist stable place semantics in DB.
This gives:
* reusable intelligence
* explainability
* less recomputation
* better downstream consistency
________________


C) Dynamic Session Context Inference
At runtime:
* infer what context is active right now
* score all nearby candidates against it
This gives:
* freshness
* time sensitivity
* route sensitivity
* human-like adaptability
That combination is the sweet spot.

4) How to Populate the Context Engine
Now let’s get practical.
There are 2 separate population pipelines:
________________


PIPELINE A — Build Stable Context Zones
This runs offline / batch / enrichment mode
Used to populate:
* context_zones
* entity_context_affinity
________________


PIPELINE B — Infer Live User Context
This runs at request/session/feed time
Used to populate:
* runtime_context_state
________________


5) PIPELINE A — Stable Context Zone Builder
This is the foundational job.
You should run this:
* per destination
* per city
* per region
* on schedule
* or when destination data changes
________________


STEP A1 — Define Zone Seeds
You need seed points to evaluate context around.
These can come from:
* major anchors
* important attractions
* destination centers
* clusters of entities
* manually defined district centers
________________


Recommended Seed Sources
Priority order:
1. major anchor attractions
2. subanchor attractions
3. known district centers
4. dense restaurant / experience clusters
5. scenic clusters
________________


Example
If a city has:
* old town square
* marina walk
* sunset beach access
* central bazaar
Each becomes a zone seed candidate.
________________


STEP A2 — Pull Nearby Evidence Around Each Seed
For each seed, fetch nearby entities.
Recommended radius by density:
Dense cities / old towns
250–400m
Resort / waterfront / beach zones
400–800m
Scenic / rural / hill areas
600–1500m
________________


Pull nearby:
* sights
* restaurants
* experiences
* anchors
* route connectors
* semantic tags if available
Also compute:
* water proximity
* elevation hints
* pedestrian density proxies
* nightlife density
* shopping density
________________


STEP A3 — Compute Context Signals
For each seed, compute normalized scores:
________________


Example signal groups
A. Place Pattern Signals
* % of scenic entities
* % of food entities
* % of nightlife entities
* % of heritage/cultural entities
* % of waterfront-view entities
________________


B. Environmental Signals
* waterfront proximity
* elevation prominence
* walkability / pedestrian concentration
* road pressure / calmness
________________


C. Naming / Semantic Signals
Examples from names:
* “Beach”
* “Harbour”
* “Marina”
* “Old Town”
* “Sunset”
* “Viewpoint”
* “Bazaar”
* “Promenade”
This can be lightweight but still useful.
________________


STEP A4 — Score Primary Context Candidates
For each zone seed, compute all candidate primary contexts.
________________


Recommended Formula
primary_context_score(context) =
 0.28 * nearby_entity_pattern_score
+ 0.22 * anchor_semantic_score
+ 0.18 * geography_signal_score
+ 0.14 * pedestrian_behavior_score
+ 0.10 * route_alignment_score
+ 0.08 * naming_signal_score


Normalize to:
0 – 100
Choose highest-scoring context as:
* primary_context
Keep next strongest 2–3 contexts as latent backups if useful.
________________


STEP A5 — Score Secondary Contexts
Now compute finer subcontexts.
________________


Recommended Formula
secondary_context_score(subcontext) =
 0.30 * micro_cluster_match
+ 0.20 * entity_density_signal
+ 0.18 * route_micro_position
+ 0.14 * dwell_pattern_signal
+ 0.10 * time_of_day_relevance
+ 0.08 * naming_signal


Choose:
* top 1 = active_context_zone
* next 2–4 = secondary_contexts
________________


STEP A6 — Compute Context Confidence
Recommended formula:
context_confidence =
 0.40 * top_context_margin
+ 0.25 * signal_density
+ 0.20 * anchor_support
+ 0.15 * route_consistency


Range:
0.00 – 1.00
This is extremely useful later.
________________


STEP A7 — Write to context_zones
Once zone scores are computed:
insert/update:
* zone center
* radius
* primary context
* active subcontext
* secondary contexts
* confidence
* density signals
* environmental signals
This becomes your place semantic map.
________________


6) PIPELINE A — Entity Context Affinity Builder
Now that you have stable zones, you score entities against them.
This is one of the most important ranking assets in the system.
________________


STEP B1 — For each context zone, fetch candidate entities
Use:
* entities inside zone radius
* optionally entities within soft overflow radius
Example:
* zone radius = 400m
* overflow radius = 650m
Overflow allows:
* scenic hill lookouts
* slightly detached restaurants
* route-support entities
________________


STEP B2 — Compute Entity Context Affinity
This is the core score.
________________


Final Recommended Formula
context_affinity_score =
 0.24 * distance_score
+ 0.18 * semantic_match_score
+ 0.14 * category_match_score
+ 0.14 * line_of_sight_score
+ 0.12 * review_signal_score
+ 0.10 * time_fit_score
+ 0.08 * cluster_fit_score


Normalize to:
0 – 100
________________


7) Exact Definition of Each Score Component
Now let’s define each practically.
________________


7.1 distance_score
This should not be a blunt linear distance.
It should be context-sensitive.
________________


Example logic
Old town / market / heritage lane
Decay faster:
* 0–80m → excellent
* 80–180m → strong
* 180–350m → moderate
* 350m+ → weak
Waterfront / beach / promenade
Decay slower:
* 0–150m → excellent
* 150–350m → strong
* 350–700m → moderate
Hill / scenic / ridge
Allow irregularity:
* 0–200m → excellent
* 200–500m → still strong if route-compatible
________________


Suggested output
Normalize:
0 – 100
________________


7.2 semantic_match_score
This is one of the strongest components.
It answers:
“Does this feel like the kind of thing that belongs here?”
________________


How to compute
Use:
* category/subcategory
* tags
* editorial labels
* optional review phrase extraction
* manual mappings
________________


Example semantic mappings
beach context
Strong matches:
* beach club
* sea-view café
* sunset viewpoint
* surf activity
* boardwalk food
* casual outdoor dining
Weak matches:
* indoor business lunch venue
* office-like chain café
* formal museum
________________


old town context
Strong matches:
* heritage site
* artisan lane
* hidden café
* local bakery
* small plaza dining
* walking attraction
Weak matches:
* highway-side drive-in
* suburban big-box feel
________________


marina context
Strong matches:
* seafood
* cocktail bar
* waterfront dining
* dock walk
* evening social spots
________________


Output
0 – 100
________________


7.3 category_match_score
This is more structured than semantic match.
This asks:
“Is this item category naturally expected in this context?”
Example:
heritage lane
* sight → high
* artisan shopping → high
* small café → high
* loud nightlife → lower
food strip
* restaurant → high
* dessert → high
* utility stop → moderate
* museum → low
scenic zone
* viewpoint → very high
* photo stop → high
* café with view → high
* enclosed arcade → low
________________


7.4 line_of_sight_score
This is especially important in scenic destinations.
This answers:
“Does the entity visually or spatially participate in the place?”
Examples:
* sea-facing terrace → high
* directly on boardwalk → high
* hidden side alley behind context → moderate
* detached indoor basement → low
________________


If you don’t have true GIS / visibility yet
Use proxies:
* waterfront distance
* same road / same promenade
* same viewpoint edge
* “sea view”, “viewpoint”, “terrace”, “rooftop” tags
* same-facing cluster
Very workable in V1.
________________


7.5 review_signal_score
This is not rating.
This is contextual validation from users.
This asks:
“Do reviews imply this is especially fitting here?”
Examples:
* “great after sunset”
* “perfect sea views”
* “best stop while walking old town”
* “nice place to cool off after the climb”
That is incredibly valuable.
________________


V1 practical version
Even if you don’t do NLP yet, approximate with:
* high review count in matching cluster
* category-local popularity
* editorial/context tags
* later upgrade to phrase extraction
________________


7.6 time_fit_score
This asks:
“Does this item fit the likely time behavior of this context?”
Examples:
* brunch café in morning promenade → high
* sunset point at golden hour → very high
* bar at 11 PM in marina → high
* beach shack lunch at 2 PM → high
* loud club at 10 AM → weak
________________


Important note
This score should use:
* entity operating hours
* daypart fit
* context type
* likely user state
This score will become even stronger when connected to your Environment + User State modules.
________________


7.7 cluster_fit_score
This asks:
“Does this entity belong to a coherent semantic pocket?”
Examples:
* restaurant inside dining cluster → high
* isolated café between unrelated entities → lower
* viewpoint in scenic chain → high
This is extremely useful for removing weird nearby outliers.
________________

9) Runtime Context Inference (Live Session Layer)
Now we move from stable place truth to live user truth.
This is where the engine becomes dynamic.
________________


STEP C1 — At feed request time, gather runtime inputs
Need:
* user_lat
* user_lng
* trip_id / session_id
* nearest anchor
* route direction
* current time/daypart
* user stage (arrival / exploring / winding_down)
* nearby matched context zones
________________


STEP C2 — Match user to best context zone
Find all context zones within practical proximity.
Recommended:
* immediate match radius = zone radius
* soft match overflow = +25% to +40%
Pick best zone using:
runtime_zone_match_score =
 0.35 * proximity_to_zone_center
+ 0.25 * route_alignment
+ 0.20 * nearest_anchor_match
+ 0.10 * zone_confidence
+ 0.10 * current_time_compatibility


Best result becomes:
* matched_context_zone_id
________________


STEP C3 — Adjust for live route/time state
Now adapt the stable zone to the live moment.
Example:
Same promenade zone can become:
At 10 AM
* route_context = exploration
At 1 PM
* route_context = food_window
At 6:30 PM
* route_context = golden_hour
At 10 PM
* route_context = night_out
This is why static context alone is not enough.
________________


STEP C4 — Write to runtime_context_state
Store:
* current primary context
* current active subcontext
* route context
* context signature
* confidence
* inference source
This becomes the live semantic state used by feed generation.

3) ZONE DETECTION — EXACT COMPUTATION
________________


STEP 1 — Fetch Nearby Entities (Core Query)
This is reused everywhere.
________________


SQL (MySQL compatible)
SELECT 
  'sight' AS entity_type,
  s.id AS entity_id,
  s.lat,
  s.lng,
  s.category,
  s.subcategory,
  s.rating,
  s.review_count
FROM sights s
WHERE ST_Distance_Sphere(POINT(s.lng, s.lat), POINT(:lng, :lat)) <= :radius


UNION ALL


SELECT 
  'restaurant',
  r.id,
  r.lat,
  r.lng,
  r.category,
  r.subcategory,
  r.rating,

function distanceScore($distanceMeters, $context) {
  if ($context === 'old_town') {
    if ($distanceMeters <= 80) return 100;
    if ($distanceMeters <= 180) return 80;
    if ($distanceMeters <= 350) return 60;
    return 30;
  }


  if ($context === 'beach' || $context === 'waterfront') {
    if ($distanceMeters <= 150) return 100;
    if ($distanceMeters <= 350) return 85;
    if ($distanceMeters <= 700) return 65;
    return 40;
  }


  return max(0, 100 - ($distanceMeters / 10));
}

function assignRole($score, $semantic, $distance) {
  if ($score >= 85 && $semantic >= 80) return 'core_fit';
  if ($score >= 70) return 'supporting_fit';
  if ($distance > 400 && $score >= 60) return 'transition_fit';
  if ($semantic >= 85 && $score < 70) return 'specialist_fit';
  if ($score >= 60 && $semantic >= 60) return 'scenic_fit';
  if ($score >= 50) return 'utility_fit';
  if ($score >= 30) return 'weak_fit';


  return 'context_breaker';
}
